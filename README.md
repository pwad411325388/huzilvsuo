# 沪紫律所股票索赔小程序一期

本地验收版。原生微信小程序提供股民、券商及销售三端。PC 浏览器提供运营后台。共用本地业务接口和 SQLite 数据。

## 启动

需要 Node.js 24 或更高版本。首次启动前安装锁定的依赖。

Windows 已安装依赖后，可双击项目根目录的 `启动本地后台.cmd`。启动器会复用已运行的健康服务，或在后台启动本地服务，并显示后台地址 `http://127.0.0.1:7101/admin`；随后在浏览器打开或刷新该地址。关闭启动窗口不影响后台运行。未设置自动启动时，电脑重启后需要重新双击启动。日志保存在 `.runtime/`，不会上传仓库。端口被其他程序占用时会提示，不会自动关闭其他程序。

如需重启电脑后自动恢复服务，在项目目录运行一次：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/configure_autostart.ps1
```

该设置只作用于当前 Windows 账户，登录后隐藏启动服务，不自动打开浏览器、不需要管理员权限。重复执行会更新同一个启动项；服务已运行时会复用。项目移动后需重新运行设置。要取消，在上述命令末尾加 `-Disable`，不会停止当前服务。

```powershell
$env:LOCAL_TEST_ACCOUNTS = '1'
npm ci
npm start
```

上面的开关仅供本地验收。首次启动会为测试库创建后台验收账号 `local-admin`，密码为 `LocalAdmin!012`。它仅在尚无管理员时生效。已有管理员以原凭据登录。开启测试模式时可使用虚构券商和案件样例。默认服务只监听 `127.0.0.1:7101`。

需要用自定的首个后台账号时，在首次启动前设定 `APP_ADMIN_ACCOUNT`、`APP_ADMIN_PASSWORD`，可选 `APP_ADMIN_NAME`。关闭 `LOCAL_TEST_ACCOUNTS` 后，新数据库不会生成虚构账号或业务样例。

SQLite 默认使用 `.runtime/demo.sqlite`。用 `DEMO_DB` 指定隔离的测试库或 `:memory:`。`DEMO_CASE_CUTOFF` 可设为 `YYYY-MM-DD`，创建数据库时写入，默认取上海时区当月首日。正式案件分界日由业务确认。切换测试端口可用 `DEMO_PORT`，监听地址可用 `DEMO_HOST`（默认回环）；原生小程序接口统一在 `miniprogram/network-config.js` 配置。

## 在微信开发者工具验收

用微信开发者工具导入项目目录，`project.config.json` 已指定 `miniprogram/` 作为小程序目录。点击「编译」，普通编译默认显示登录页。模拟器默认使用本机 HTTP；手机真机请先双击 `启动真机调试.cmd`，再重新编译并扫码。完整操作与防火墙说明见 [真机局域网调试](docs/lan-debug.md)。正式版需要配置公网 HTTPS 接口。

1. **股民自助注册。** 登录页点「首次使用？注册股民账号」。填未使用的虚构手机号和自设密码（至少 8 位）。登录后打开「我的」，顶部显示手机号作为初始名称及登录账号。修改显示名称后退出，仍用原手机号和原密码登录。留资姓名和联系电话在独立的留资业务区展示。
2. **后台开通销售账号。** 用后台账号登录 [PC 后台](http://127.0.0.1:7101/admin)，进入「账号管理 → 销售账号开通」。新业务选择「新增销售」，为有历史券商绑定的销售开户时，选择对应旧销售记录。填写销售姓名和专用账号后提交。新销售和券商的默认初始密码统一为 `12345678`。首次登录小程序时，用初始密码设置个人密码，再用新密码登录。销售端首页登记券商合作，「我的」显示登记姓名和登录账号。
3. **后台开通券商账号。** 销售登记合作后，登录 PC 后台，在「账号管理 → 券商合作与开户」按券商名称、账号或合作负责人搜索，也可筛选待开户、已开户或已注销。待开户排在最前，每页 20 家。点击「展开开户」，填写专用账号并点击「开通账号」。已开户记录默认收起，点击「查看资料」展开。开户后保留当前搜索条件。券商按上一步的首次登录流程设置个人密码，在首页看推广与统计，在「我的」看名称、账号及台账。
4. **调试扫码归属。** 退出登录，在微信开发者工具的编译模式中选择「券商 A 测试扫码」或用开户后取得的推广码创建场景，页面设为 `pages/home/index`，参数为 `scene=推广码`。未登录时先从 A 场景编译，再从 B 场景编译，从同一个注册入口完成注册。后台查看首次来源和当前券商均为 A；券商台账与合作统计按当前渠道归属读取，该客户之后提交的留资自动交给券商 A 绑定的销售。授权改归后重复扫码也保持改归结果。浏览器可用 [券商 A 链接](http://127.0.0.1:7101/?promo=DEMO-A) 和 [券商 B 链接](http://127.0.0.1:7101/?promo=DEMO-B) 在同一浏览器会话验证。直接注册的账号初始无归属，首次有效扫码可补绑。
5. **业务联动。** 股民从首页展开「提交咨询资料」，提交后在「我的 → 我的股票登记」查看记录。后台录入客户签约结果、创建新案件并更新状态。销售和券商可切换看板指标，后台可筛选并导出 Excel。查询和导出使用同一套业务编号、销售姓名和日期字段。

退出登录在三个小程序端的「我的」顶部。当前会话会被服务端撤销。保留的有效会话可以在下次打开时恢复，默认有效期七天。

同一浏览器可同时打开 [PC 后台](http://127.0.0.1:7101/admin) 和多个 [业务端](http://127.0.0.1:7101/) 新标签页。每个业务标签页可分别登录股民、销售或券商账号，刷新沿用各自登录态。升级前从首页进入后台的旧登录态需在新后台入口重新登录一次。

## 券商推荐与公司派单

- **已确认业务规则：** 券商推荐客户提交留资时，当前券商绑定的销售直接成为该条留资的经办人。股票未配置或公司负责人不同，仍按券商派单。券商缺少可用销售时进入待分配。自然流入的留资按股票公司负责人派单。同一股民不同股票留资可以分派给不同销售，查询权限按留资隔离。
- **配置入口：** 后台「公司与派单 → 新增公司派单配置」填写公司名称、股票代码、股票别名及负责销售。负责销售必须已开户且账号正常。对于自然流入的留资，名称/别名与代码精确匹配同一公司才按公司派单；冲突、无法匹配、配置停用或销售不可用时进入「新留资待分配」。别名与代码不可占用另一公司的配置。新增配置不会回填旧留资，修改负责人只作用于之后提交的新留资。
- **人工处理：** 后台「公司与派单」筛选新留资待分配、历史待核对、已分配或全部，点击「核对并分配 / 核对与转派」。选择经办销售并填写说明。自然流入留资还需核对公司，券商推荐留资的公司资料可选填。原始股票输入保留。转派后旧销售不再能查看该条记录，由新销售查看资料和案件进度。多管理员同时修改会检测版本冲突。
- **使用端：** 销售网页/小程序首页「我的客户与股票」统一展示名下客户的全部授权股票记录，按姓名、电话、股票名称或代码搜索，支持全部、本月及自选日期筛选。销售通过小程序查看客户资料、股票记录和案件进度，不要求录入日常沟通。「我的」提供销售数据统计，包含已关联的律所历史登记。
- **本地实现默认，非正式业务定稿：** 升级时按当前券商绑定的可用销售补派尚无经办人的推荐留资。既有经办人及跟进记录继续保留。股票代码输入扩到 20 字，支持本地配置字母、数字、点、短横线，并统一大小写及全半角匹配；没有接行情库，也不代表已确认支持任何具体市场。正式支持市场及签约业绩归属仍待业务确认。

验收可配置「虚构公司甲 / TSTA → 销售 B」和「虚构公司乙 / 000002 → 销售 A」。让券商 A 绑定销售 A。提交公司甲时，自然注册客户的留资归销售 B，券商 A 推荐客户的留资归销售 A。同一自然流入客户再提交公司乙，只该条归销售 A。股票无法匹配时，自然流入的留资进入待分配，券商推荐的留资仍交给销售 A。调整客户券商或券商合作负责人不应改变这些留资经办人。更改公司配置不能自动挪动已分派留资。

## 后台数据模块

采用深蓝品牌栏、左侧功能导航、统计卡片与明细表格，数据来自当前数据库；未复制或导入原型真实客户数据。返佣、金额、奖励控件及相关指标不展示，原存储字段保留。

- **数据总览：** 默认显示截至今天的全部数据，合并小程序留资与律所历史登记，支持「全部」「本月」和自选起止日期。8 张卡片为留资与登记、客户档案、来源渠道、待分配/关联、在办案件、已结案、历史登记和已签约档案。点击任一卡片（包括 0 条）查看同一日期范围的明细，支持姓名、电话、股票、渠道或销售搜索，每页 20 条，返回时保留日期范围。搜索只缩小明细，不改变卡片统计范围。客户档案在全平台按确认身份或完整姓名和有效手机号合并，缺资料的记录独立待核，不能简单相加各销售档案数。需要处理区和最近登记也跟随当前日期范围。
- **销售看板：** 合并小程序经办留资与已关联销售账号的律所历史登记，展示来源渠道、登记记录、客户档案及已确认的在办/已结案进度。可按销售筛选，点击数量进入明细，按姓名、电话、股票或渠道检索，每页 20 条。来源渠道包含合作券商和原表中的来源分类，同一来源可涉及多位销售。客户档案按已确认身份或完整姓名和有效手机号合并，其余登记保留独立待核档案，跨销售档案数不可直接相加作为平台人数。未把这些数量定义为正式业绩归属。
- **渠道管理：** 渠道合作负责人、账号状态、合作日期及客户/留资/案件计数；自然流入单列但不创建券商记录。可调整合作负责人、查看该渠道案件或跳转账号维护。
- **客户案件：** 客户、股票、来源渠道、经办销售和状态筛选。案件按件列示，持久化可读编号 `AJ-000001`；展示对应留资的经办人，保留录入和状态更新。统计包含全部历史登记的可识别进度和小程序案件，支持全部/本月/自选日期；当前测试分界日只约束新增案件录入，不再截断全量统计。未知进度和其他阶段单独筛选，不伪造案件状态。
- **数据报表：** 留资与登记、客户档案、来源渠道、客户案件、已签约档案和销售汇总六类，与数据总览及渠道/案件页共用读取和分类规则。按期间、销售、来源、数据来源、当前状态和关键词查询，页面每页20条；Excel导出使用已应用筛选的全部结果，不受当前页或未提交草稿影响。历史登记不变成可编辑小程序客户，签约只使用明确证据；无财务列。旧兼容导出接口仍仅用于原小程序业务范围。

### 列表排序约定

排序是整个查询结果的规则，先排序再分页；导出与对应报表使用同一顺序。注销账号及其历史业务继续保留，可筛选查看。

| 列表用途 | 默认顺序 |
| --- | --- |
| 销售统计、销售汇总报表 | 正常 → 待开户 → 已注销；同组客户档案数多的在前，其次登记条数，再按中文姓名及固定编号 |
| 来源渠道统计 | 有效来源 → 待开户券商来源 → 仅注销券商来源；同组按客户档案数、登记条数降序。历史来源分类不当作未开户账号 |
| 账号名单及人员选择 | 正常 → 待开户 → 已注销；具体次序在列表旁说明，选择器按中文姓名排列 |
| 券商开户、批量开户预览 | 需要开户或关联的事项优先，已完成或已注销项靠后，不改变既有账号编号 |
| 留资、客户、案件、个人台账 | 登记日期从新到旧，缺日期末位；同日采用固定次序，不随翻页重排 |
| 后台律所登记台账 | 材料登记日期从新到旧，缺日期末位；同日按原表行号、登记键排序，保留原始登记号 |
| 待分配 / 待核对 | 新待分配 → 历史待核对 → 历史待关联；每组登记日期从旧到新，缺日期在组内末位 |
| 客户精确搜索 | 完整姓名、电话或账号匹配优先，再按稳定次序排列，保留搜索相关性 |
| 实际签约记录、审计日志 | 分别按实际签约日、操作时间从新到旧 |

共享比较规则位于 `web/list-order.js`。状态分组只用于账号、人员和来源名单，不把由已注销销售经办的客户或案件从正常日期序列中移走。排序回归覆盖超过一页的同日、同值数据，核对翻页、返回和完整导出无重复、无遗漏。

### 律所登记台账

在 PC 后台打开「律所登记台账」可分页检索工作簿中的登记记录。每行对应原表的一条登记，相同股民可能涉及多只股票或多次登记。台账保留原表行号、登记销售、股票及可识别的进度，材料登记时间和立案时间分别展示。历史登记与小程序留资分别存储，在销售「我的」统计中按账号关联一并展示，不会生成新的派单或伪造签约记录。

管理员可在台账中打开「按销售姓名批量开户」。预览会列出每位销售、原表标记、登记条数和处理方式。新开户的销售使用统一默认初始密码 `12345678`，可点击「保存新账号清单」交付。姓名前的单个业务星号与同名销售合并，职务、同名冲突及有争议的归属留待管理员核对。重复执行批量开户会沿用已开户销售的现有密码。销售首次登录时设置个人密码并重新登录，首页「我的客户与股票」与已有客户一起展示关联的股票记录，在同一个搜索框检索。

在台账行点击「关联账号」也可以单独关联销售或股民账号，核对身份、来源及影响条数后确认。股民关联同时符合登记姓名和单一有效合同手机号的记录，用已注册的股民账号进入小程序「我的 → 我的股票登记」即可与自己提交的股票记录一起查看。管理员可在同一处解除关联。

后台「销售看板」直接读取同一份台账快照和账号关联。更新工作簿快照或调整关联后，刷新看板即可读取新结果，重复刷新不会产生重复留资。原表中的股票登记按历史登记展示，不会伪造客户注册身份、券商登录账号、推广码或跟进记录。像「百度优化」「投资快报」这样的共享来源按每位销售对应的登记统计；来源不明的记录保留为待核对来源。未关联到具体销售的历史登记有独立入口，需核对后再关联账号。

本地数据源默认为项目上级目录的 `测试数据/诉讼组—股民登记表格.xlsx`。在 WPS 或 Excel 保存修改后，后台点击「从本地表格更新」。系统读取「股民登记总表」并在校验完成后更新本地快照。更新时需要 Python 3，使用标准库。部署到其他目录时可通过 `REGISTRY_WORKBOOK` 指定工作簿绝对路径，`REGISTRY_PYTHON` 可指定 Python 可执行文件。更新方向为工作簿到应用，账号关联在后台维护。

### 销售累计与期间统计

销售登录网页或小程序后，打开「我的 → 我的数据」。默认「全部」统计截至今天的累计记录，包含当前经办留资和已经关联到该销售账号的律所登记。券商合作关系单独计入来源卡；已转派给其他销售的股票与案件不再出现在原销售的经办档案、案件或详情中。点「本月」使用上海时区当月首日至今天，也可选起止日期后点「按日期查看」。卡片与明细使用相同范围，业务端明细每页 5 条。

- **来源渠道：** 合并当前负责的券商、经办留资的来源（含自然流入）及历史登记中已识别的来源名称。历史来源名称只用于统计，不会自动开通券商账号或建立归属。
- **客户档案：** 先按明确关联的股民身份合并，再按完整姓名和有效手机号核对。缺少手机号、未关联身份的历史记录保留独立档案，单位为「份」，不将其视为已经确认的独立客户人数。
- **已签约客户：** 计实际签约记录、公司同步的明确签约状态，以及历史登记中已立案及后续阶段的客户。**用户确认（2026-11-20）：历史仅已立案及后续阶段可按已签约统计。** 同一客户按既有身份/姓名电话规则合并；未立案、立案退回、待受理或只有提交立案的记录不据此推定签约。原表部分退回记录也填有立案时间，因此空白或待核对进度不能仅凭日期升级，须有独立明确的正向状态。公司正式更正或清空进度时优先采用最新状态；进度测试仅改变展示，签约统计读取匹配备份中的正式证据，失效备份不采纳模拟值。此规则仅用于历史登记，不把普通系统留资自动改为已签约，也不补造实际签约日期。后台筛选销售时只采用该销售范围内的签约依据，平台全部仍按客户合并。
- **已结案：** 包含有明确结案状态的本地案件和历史登记；公司同步的最新状态优先。历史数据按结案登记记录计件。

日期筛选按每条留资/材料登记日期选取数据，再合并客户档案；老客户新增股票按本次留资日进入期间，摘要不混入范围外股票。展示这些记录当前的签约与结案情况。券商来源按合作日期或本期经办留资出现日期计入，历史来源按材料登记日期。原表没有签约日期、结案日期，因此「本月」不是当月实际签约或结案事件统计。缺少有效日期的记录仅纳入「全部」，页面会提示。销售间仍按各自授权范围读取，解除台账关联后重新进入页面即不再计入。

**用户确认（2026-11-18）：上述登记日期口径仅用于当前测试。正式上线前必须切换为各指标的实际发生日期。** 客户登记按实际登记日期，渠道合作按实际合作日期，签约按实际签约日期，结案按实际结案日期。卡片、明细和期间汇总须使用同一业务事件日期，不能用材料登记日期或数据同步时间替代签约、结案日期。

上线前需补齐公司数据源的签约、结案事件日期及对应稳定记录标识，并验证跨月、起止日期边界和累计/明细一致性。历史记录缺少实际发生日期时保留为日期待核，不推算或补造日期，不计入无法确定归属月份的期间统计。当前实现尚未完成这项正式口径切换，不能将测试口径作为正式上线验收结果。

后台「数据总览」沿用上述测试日期口径。小程序记录按留资登记日期，历史记录按材料登记日期选取，客户档案按选中记录在全平台去重，案件和签约展示这批记录当前已确认的状态。「本月」从上海时区当月首日至今天，自选日期包含首尾两天；缺少日期的记录只进入全部累计，未来登记日期暂不计入。来源渠道包括合作登记日期符合条件的券商和选中记录中出现的可识别来源类别，不据历史来源创建券商账号。后台已签约卡片、客户筛选、报表与销售及券商当前已签约客户共用上述历史签约判定；导出实际签约日期缺失时留空。

「待分配/关联」包括小程序尚未分配或销售账号不可用的留资，以及历史未关联销售或需调整销售的登记。需要处理区分列新留资待分配、小程序历史留资待核对、历史登记待关联/调整，点击后仍使用当前日期范围。历史缺少跟进状态本身不等于待分配。后台总览使用同一份只读台账快照，刷新不会复制客户、留资或案件。

### 原生小程序案件进度

在微信开发者工具打开本项目并编译。股民从首页优先卡查看当前补料记录，也可从「最近记录 → 查看全部」逐案查看。同一留资下的多个案件各计一件，未建案留资和待核对登记分别统计。「我的 → 我的股票登记」按原登记归组。销售从首页「我的客户与股票」搜索并点记录进入。所有记录使用同一入口，返回后保留查询、日期范围和页码。旧登记页路由也进入统一列表，不再提供仅查原表的使用端入口。

详情使用竖向圆点连线。已签约待立案环节展示三节点：绿色「留资与签约 / 已签约」（角色旁注不变）、黄色锚点「立案 / 立案材料准备中」、灰色「立案 / 已提交立案」。黄色项仅作此环节的展示引导，不修改实际案件状态或补造日期；若公司明确指定其他下一路线，仍按指定路线展示。其他环节保留绿色当前节点、灰色下一节点，已结案只显示终点。阶段名称用大字，右侧小字显示状态及原有旁注，下行显示对应日期；例如大字「立案」、右侧「已提交立案」，下一节点大字「一审」、右侧「一审待开庭」。网页、原生小程序和后台双角色预览一致，移除上方重复的阶段和状态。股民已签约且待立案时保留「已签约 · 待立案」，销售保留「已签约」及有权限查看的真实合同号。立案补件分别显示股民「待您补充材料」和销售「待补充材料」，债权申报补件两端均为「待补充材料」。股民接口不返回合同号。缺少具体节点时显示已有粗状态或待同步提示。

节点日期只采用该记录、该阶段的有效真实事件：直接留资使用创建日期，唯一确认对应股票的签约使用实际签约日期，原登记的已提交立案可显示同一行的立案日期（不称提交日期）。不借用父客户或其他案件的日期；测试节点不继承真实事件日期。没有对应日期时当前节点显示「日期待补充」，黄色准备节点和灰色下一步不显示日期。其他已知登记、签约和立案日期仍保留在详情字段中，不编造日期或预计时长。

列表与详情共用股票记录的当前状态：明确的公司快照优先，空快照表示清空；没有该记录快照时读取关联案件的当前状态。没有案件时，客户级实际签约仅在签约日当日及此前只有本条候选股票记录、且本条登记日期有效时用于确认「已签约」。候选包含该客户不同经办销售的留资和明确关联账号的登记，缺日期保守计入；有多条候选时显示「签约对应记录待核对」。签约后新增股票不继承此前签约，客户级签约人数统计保留。签约凭据说明不充当合同号，不以另一客户的签约或登记日期推算签约。此逻辑只读取数据，不改写已有记录。

下一节点使用已确认的组内顺序、「待立案 → 立案材料准备中」、「已提交立案 → 一审待开庭」、「一审判决已生效 → 执行中」及「二审判决待生效 → 执行中」。执行获赔后的默认路线为「执行 · 获赔 → 获赔 · 待支付 → 获赔与结案 · 赔款已到账 → 已结案」。当前为「执行 · 获赔」时，下一节点以灰色展示「获赔 · 待支付」。到账以来源记录的实际状态为依据。公司明确同步的下一路线优先，例如提交立案后需要补材料时，使用该记录的补件路线；清空明确路线后回到默认流程预告。其他未确认跨阶段路线显示灰色「后续进度待确认」。下一节点始终表示后续步骤，不表示已经发生或法院已受理；执行或债权阶段的获赔不等于股民赔款已到账。

2026-11-18 本地工作簿的 30,900 条登记中，4,989 条可以确认当前节点。已结案 3,320 条，一审待开庭 681 条，二审上诉待开庭 338 条，执行中 448 条，已调解待支付 202 条。一审待开庭的组合依据是明确的「已立案未开庭」、可辨认的一审案号且无退回或后续程序冲突。结案标记只确认结案本身。其余登记根据证据展示已有粗状态、待核对或未同步。

正式对接需要公司系统提供每条留资、案件或历史登记的稳定标识、阶段、当前节点、版本，以及销售有权查看的独立合同号。判决生效、补料、发回重审、债权申报结果、股民到账等节点需要公司确认阶段与状态字典。付款经手方和股民实际到账要有各自的来源字段。本地原表的合同备注、合同联系电话和案号均有各自用途，主表目前缺少独立合同号。

可在服务所在机器用 `node scripts/sync_progress.mjs <快照.json> --db <现有数据库文件>` 单向同步公司导出的 JSON 数组。`kind` 支持 `lead`、`case`、`registry`，`id` 分别取本地留资 ID、案件 ID、台账内部登记键。接正式接口时须先维护公司记录与本地记录的一一对应。每条快照提交递增整数 `revision`、成对的 `stage` 和 `node`、可选的 `contractNumber`，以及成对的 `nextStage` / `nextNode` 说明已确认的下一路线。完整快照优先于台账，显式提交两个 `null` 清空当前节点，省略合同号或下一路线会清空对应已同步字段。无当前节点、已结案或与当前完全相同的节点不能设置下一路线。重复同版同内容可重试，版本冲突会整批回滚。阶段和节点取值见 [进度字典](./progress-dictionary.mjs)。

公司快照仍可通过 `completedNodes` 保留本阶段已完成节点的证据，兼容原有导入。新版本省略该字段或提交空数组会清空该快照的完成证据；使用端不再展开历史完成节点。历史登记日期不用于推算签约、判决或到账。

### 后台进度测试

本地运营后台的「进度测试」用于手动验收三端显示。搜索客户姓名、电话或股票，核对客户、负责销售和股票/案件后，选中**一条具体记录**。选择阶段和当前状态，点击保存；后台同时显示股民、销售两种真实投影，使用端刷新或重新进入该条记录即可核对。普通后台记录报表也显示同源的股票当前进度。

此入口默认关闭。项目本地启动器通过 `LOCAL_PROGRESS_TEST=1` 开启；未开启时隐藏入口并拒绝测试接口。独立启动验收服务时也需要显式设置该环境变量，正式环境不启用。

选项直接来自销售版进度字典，共八个阶段：留资与签约、立案、一审、上诉与二审、调解与和解、执行、债权申报、获赔与结案。销售「已签约」对应股民「已签约」旁注「待立案」；补材料文案和合同号权限由原角色规则生成。在更多测试项中可填写测试合同号，或明确指定下一路线；不指定时使用原流程默认的下一步，无法确定路线时提示待确认。

保存只覆盖所选记录的当前进度，不改其他股票、真实签约日期、派单或原案件字段；测试无独立案件的股票不会新建案件；股民首页按该股票当前显示的一审、二审、执行或获赔结案节点计为一件展示案件，正式后台/销售统计不因此增加案件数。测试期间允许向前、向后切换状态，旧立案证据不干扰本次明确的测试节点。首次测试前的原进度会被保留，多次修改后点击「恢复原进度」即可回到开始测试前。测试使用独立的编辑代次，不占用公司同步版本号；公司下一版数据仍能正常接入。记录已被其他管理员或公司同步更新时，旧表单不能覆盖；恢复也不会回盖更新后的公司数据。测试修改和恢复均有管理员权限校验、版本校验和审计记录。

## 股民首页摘要与查看全部

已登录股民的 `GET /api/view` 附带 `investorHome`：`totalRecords`、`caseCount`、`leadCount`、`unclassifiedCount`、`countingNote`、`attentionCount`、`attention`（一条或 `null`）及 `recent`（最多两条）。摘要只读取本人留资及明确关联的登记；不通过同名、同手机号或同股票猜测授权和跨来源合并。

首页按具体案件及未建案留资计数：一条留资有多个案件时分别按案件 ID 计数，不重复计父留资；没有独立案件的留资，若自身当前快照已进入一审、二审、执行或获赔结案阶段，则首页计为一件展示案件，不再列为未建案留资；其他状态仍计留资，灰色下一步或黄色准备节点不作为计案依据。本地测试按同一当前状态展示，恢复或退回时重新计算；只调整展示分类，原详情键不变，不创建案件，后续有独立案件时按子案替换而不重复计父留资。登记按有效立案日期、明确的原表已建案状态或正式的一审/二审/执行/结案节点确认案件，其余单列待核对；模拟节点只参照当前有效备份中的正式状态。`totalRecords = caseCount + leadCount + unclassifiedCount`。

每个条目都有 `id`（含类型）、`kind`、`progressId`、`stockName`、`stockCode`、`status`、`registeredOn`；案件带真实 `caseTitle`，点击使用既有 `/api/progress?kind=...&id=progressId`。案件登记日只取该案的登记日，不借父留资的日期。当前明确处于立案补料或债权申报补料才提醒；下一步、已完成记录不触发提醒。父留资继承案件补料时只提醒案件，有自身补料指令时保留其独立提醒目标。

股民从首页查看全部使用 `GET /api/records?presentation=home`，与摘要共用全集，默认第一页前两条即 `recent`；保留 `period=all/month/custom`、`from/to`、业务端每页5条和 `offset`，按登记日期从新到旧、同日名称与稳定ID排序，缺日期置后且仅计入全部范围。原无 `presentation` 的记录接口保持一条留资一行的口径；销售、券商和管理员不能使用首页展示参数。强制改密时 `/view` 不返回业务摘要。

## 券商统计与跨入口核对

券商首页为「渠道台账」，默认显示全部已归属数据，可选本月或自选日期，统一提供客户姓名、股票名称或代码搜索，以及全部客户、洽谈中、已签约筛选。四张卡片为我的客户、在办案件、已结案件、已签约客户，共用一份可收起的5条分页明细。搜索和客户签约筛选仅影响明细，上方概览保持当前日期范围内的总数；明细进入客户股票记录后返回保留原查询条件。客户与案件按登记日期选队列，未留资客户按注册日期；只有明确的当前 `brokerId` 归属才能访问，原表来源名称不能代替授权，不展示客户电话。「我的」集中放推广码、推广分享及账号安全，不再另设客户查询。

券商页面统一保留「已签约客户」，包含已确认签约的历史客户，不要求已有实际签约日期；本地测试按登记日期筛选。销售和券商使用端看板隐藏明细标题下及列表底部的统计口径、排序等说明，保留选定日期范围、搜索匹配数量、记录字段和分页。移除重复的累计签约卡片，不删除签约日期或记录。旧接口的 `metric=signings` 仍兼容按实际签约日期统计及下钻全部股票，供已有调用使用；缺少实际签约日期的历史状态不计入该旧事件统计，不会补造日期。所有案件列表、关联卡片与进度详情优先使用同一份公司快照；显式清空显示待核，原始录入状态仅供后台核对。

回归从同一隔离工作簿覆盖导入、重复导入、关联、换销售、解除关联、公司快照更新与清空，核对平台卡片、明细、报表导出及个人授权。维护表单仅写小程序业务，页面提供全量客户档案与历史登记台账入口，避免将不可编辑的历史资料误认为丢失。

## 使用端统一记录

券商「我的」推广区域暂用静态示意二维码，明确标注「演示占位码，暂不可扫码」，原推广码文本和分享入口继续使用本人的推广标识。网页图片为 `web/assets/promo-placeholder.png`，小程序图片为 `miniprogram/assets/promo-placeholder.png`；上线接入真实码时需同时替换图片来源及占位提示。

股民「我的」的股票登记列表统一显示本人提交和经管理员核实关联的股票记录，移除独立的「律所登记记录」检索。销售首页只有一个「我的客户与股票」列表，默认全部记录，可按客户姓名、电话、股票名称或代码搜索；券商首页的「渠道台账」统一承担客户查询，只看明确归属的客户及其已核实关联的股票，不显示电话。看板的客户卡片进入该客户的统一记录，并保留已应用登记日期范围。旧实际签约事件链接仍进入该客户的全部股票记录，并明确提示，避免上月登记、当月签约造成空列表；返回仍保留原看板期间。

统一接口 `/api/records` 在当前账号授权范围内先筛选、排序再分页（业务端每页5条），不会只查当前页或股票摘要的前8项。全部、本月、自选日期按登记日期筛选，缺日期仅计入全部。没有姓名、电话等可靠身份的档案不按同名自动合并；同一人多次登记同一股票仍保留各条记录。

已存在且授权的案件在看板、记录和详情使用相同读取范围，案件录入分界只限制新增/修改日期，不隐藏本人早期案件。后台保留表格同步、账号关联和数据来源核对能力；这不再成为使用者需要选择的查询范围。转派销售、解除关联或调整券商归属后，下次查询和详情访问立即按最新授权判断。

## 客户检索与签约

- 「客户签约」中的「调整客户归属」和「登记客户实际签约」均输入姓名检索，也可用手机号或登录账号查找。完整姓名匹配优先；同名客户展示电话、当前券商和登录账号，必须点击确认具体客户后才能保存。修改搜索内容会取消旧选择，避免误操作。
- 调整归属仅检索已有券商归属的客户；实际签约仅检索有姓名、电话和留资的客户。每批展示 20 位，可继续加载匹配结果。支持方向键选择、回车确认以及 Esc 收起结果。
- 下方「客户记录」新增「股票线索」列，可按股票名称/代码、姓名、电话、登录账号、首次或当前券商检索。每位客户只列一行，合并全部股票线索并标出重复留资条数；每页 20 位，搜索与重置不清空上方正在填写的表单。

## 账号管理与忘记密码验收

1. **查找全部账号。** PC 后台「账号管理 → 全部账号」包含股民、销售、券商和管理员。按姓名/登录账号、角色、状态筛选。待留资股民也会列出。后台顶部「账号安全」用于管理员修改自己的密码、生成个人恢复码。
2. **后台重置密码。** 找到目标账号，点击「重置密码」，输入当前管理员密码和给用户的临时密码，再确认账号与申请人身份。旧密码、全部设备会话和旧恢复码立即失效。用户用临时密码登录后，只能设置自己的新密码，完成后重新登录才能访问业务。重置当前管理员自身密码也会退出当前登录。
3. **注销和恢复。** 「注销账号」采用停用登录，保留账号标识及留资、签约、案件、渠道归属、审计记录，不执行个人资料删除。不可注销当前管理员或最后一个可用管理员。注销后所有会话与恢复码失效，券商推广码停止接纳新客户，已有客户数据和统计保留。后台可「恢复账号」，恢复后旧会话和旧恢复码仍不可用。用户名继续保留，不允许重新注册冒领历史记录。
4. **提前保存个人恢复码。** 网页/小程序登录后打开「我的 → 账号安全」，输入当前密码，生成新的恢复码并妥善保存。管理员在后台顶部「账号安全」操作。该码只显示一次，可用一次，无固定期限；重新生成、修改/重置密码、注销账号都会使旧码失效。页面关闭或退出后不再展示，服务端仅保存散列。
5. **用户自行找回。** 登录页「忘记密码」，填登录账号、已保存的恢复码、新密码和确认密码。成功后使用新密码正常登录，不自动登录。恢复码不能跨账号或重复使用；所有旧会话和恢复码失效。每个账号的恢复入口 15 分钟内最多尝试 5 次，超过需等待或由后台重新签发码；正常密码登录不会因此被锁定。
6. **未保存恢复码。** 管理员通过既有联系方式/业务材料核实账号本人后，在「全部账号 → 临时恢复码」输入管理员密码并确认核实，签发一次性临时码，30 分钟有效。将码交给本人后，由本人在「忘记密码」设置新密码。新码使此前的恢复码失效。也可采用第 2 步直接重置临时密码。系统没有自动完成线下身份核实，只有账号/手机号不构成找回凭据。

当前没有接入短信、邮件或微信身份验证，使用恢复码完成本地找回流程。恢复码设计参考 [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) 的离线恢复码、单次使用、撤销旧会话等建议。上述全部敏感账号操作记录审计，不记录密码或恢复码原文。

## 迁移与权限

- 启动时在原 SQLite 库迁移券商账号散列，并补齐既有销售业务记录。现有留资、案件、签约、券商和归属继续保留。旧临时股民身份需重新注册。注册手机号与旧留资手机号相同，也不会自动认领旧记录。
- 股民账号只可自助注册为股民。后台创建券商和销售账号。登录角色、账户标识和访问范围均取自服务端。密码按账号加盐散列，会话令牌以散列保存。浏览器使用 HttpOnly 会话 Cookie，小程序使用本地保存的会话凭证。
- 匿名推广入口由服务端验证并保存首次有效来源。浏览器用临时 Cookie 维持待关联会话，待关联记录有效期 24 小时。注册时在数据库事务里写入首次来源和当前归属。小程序本地调试沿用相同规则，正式微信侧用 OpenID 衔接仍待联调。
- 券商看板显示本渠道客户的留资姓名与后台登记的案件名称。手机号向有权销售和后台显示。当前展示与统计按当前渠道归属，正式历史归属口径待确认。
- WPS 保持在本地业务流之外，正式接入需同结构样表、编号和字段映射、测试文件授权。案件状态首期由后台维护。正式手机身份核验和账号交付流程待确认。
